# ADR-001: Populate Inventory Read Cache via Scheduled Batch Import

## Scoring rationale (from 00-options.md trade-off matrix)

Three options were evaluated against five load-bearing Meridian constraints:

| Constraint | Option A — Batch import | Option B — Pull-through cache | Option C — Event projection |
|-----------|------------------------|-------------------------------|-----------------------------|
| **SAP batch-update reality** | ✅ Import job matches SAP's native batch cadence; no real-time API required | ❌ RFC/BAPI "live" call reads same batch-refreshed snapshot as A but adds 200–600ms p95 to the hot path | ❌ SAP emits no native events; synthetic poller = Option A's job wrapped in Kafka + projection overhead |
| **Junior-team operability** | ✅ One scheduled job + one Redis store; failure = stale data, not outage; testable in isolation | ⚠️ SAP adapter + TTL logic + hot-path fallback; harder to reason about under peak load | ❌ Kafka + projection service + DLQ + schema versioning = 3 new services; requires distributed-systems expertise |
| **PSD2 SCA latency** | ✅ Confidence path and checkout path are independent; SAP never on checkout hot path | ⚠️ Cache-miss adds 400ms to confidence scoring; indirect pressure on combined page-load budget | ✅ Pre-computed view; confidence p95 bounded by Redis read only |
| **Strangler-fig coexistence** | ✅ Import job is storefront-agnostic; one Redis surface serves all three platforms | ✅ SAP adapter is also storefront-agnostic | ⚠️ Kafka deployment adds infrastructure that all three storefronts must eventually align to before migration |
| **18-month / $42M budget** | ✅ Lowest build cost; no new messaging infrastructure | ⚠️ SAP adapter + fallback handling adds ~2–4 weeks | ❌ Kafka + projection + DLQ = ~2–3 months additional engineering |

**Option A chosen.** Option B fails SAP batch reality — the live RFC/BAPI call adds 400ms hot-path latency while reading the same data the import job would have fetched, delivering Option A's freshness ceiling at Option B's latency and complexity cost. Option C fails junior-team operability — SAP's batch-only architecture forces a synthetic event poller that behaves identically to Option A's import job but requires Kafka, a projection service, and a dead-letter queue, consuming the complexity budget without improving data freshness.

---

## Context

SAP S/4HANA is Meridian's inventory source of truth but exposes no real-time query API for Phase 1 — inventory is batch-synced to the OMS with a 2–4h lag during peak. The Confidence API must score store-SKU availability on every product page load (p95 ≤ 800ms async). Placing SAP or OMS calls on the confidence scoring hot path would add 200–600ms p95 per cache miss — unacceptable latency at 600-store scale — and couples Confidence API availability to SAP uptime.

## Decision

We will populate the Inventory Read Cache (Redis / AWS ElastiCache) by running the SAP Inventory Adapter as a scheduled import job every 15–30 minutes. The job pulls inventory count snapshots from SAP S/4HANA via RFC/BAPI and POS velocity snapshots from OMS, then writes the combined `{storeId, sku, count, velocity, sync_ts}` records to Redis. The Confidence API reads only from Redis at inference time — zero live calls to SAP, OMS, or POS on the confidence request path.

## Alternatives Considered

1. **Pull-through cache with live SAP adapter (Option B)** — rejected because SAP S/4HANA exposes no transactional inventory query API for Meridian Phase 1; the RFC/BAPI call reads a batch-refreshed materialised view with the same 2–4h ceiling as Option A's import, but adds 200–600ms p95 to every cache-miss request. The architectural investment in a live-call model delivers no freshness improvement; the latency cost is paid for nothing.

2. **Event-driven materialised projection (Option C)** — rejected because SAP S/4HANA batch architecture produces no native inventory change events; a synthetic event poller is required to simulate event emission from batch snapshots. This poller is semantically equivalent to Option A's import job, but requires operating Kafka, a projection consumer service, a dead-letter queue, and schema versioning — 3 additional services for a junior Phase 1 team — without raising the freshness ceiling above 30 minutes.

## Consequences

**Positive:**
- Confidence API has zero runtime dependency on SAP availability; SAP maintenance windows do not degrade confidence scoring.
- Inventory data staleness is deterministic and bounded: worst case = import interval (30 min). The "SAP sync > 4h stale" refusal trigger evaluates the import timestamp directly — no inference required.
- Import failures produce stale data, not outages; the circuit breaker detects calibration drift and reverts to binary fallback independently of import health.

**Negative:**
- A store that sells out between import cycles will show a stale High confidence signal until the next run. The worst-case phantom window is 30 minutes, reduced from today's 2–4h SAP lag but not eliminated.
- POS velocity granularity is bounded by the OMS export cadence (currently daily); the velocity signal may be stale within a flash-sale window. The offline experiment (S3, 6 months POS history) must validate MAPE improvement at daily granularity before including velocity in the production model.

## Agent-Readable Summary

The Confidence API reads inventory state exclusively from the Inventory Read Cache (Redis). **Do not add SAP S/4HANA, OMS, or POS calls to the confidence scoring request path.** The Redis cache is populated by the SAP Inventory Adapter scheduled import job running out-of-band every 15–30 minutes; the Confidence API has zero runtime dependency on SAP availability. If Redis returns no entry for a store-SKU pair, the Confidence API must emit binary fallback status — it must not fall through to a live SAP call.
