# ADR-003: Delegate Authentication to Auth0, Keep Identity Service as a Thin Enrichment Proxy

## Context

Meridian Phase 1 must unify customer authentication across three storefront platforms (Shopify Plus DE/AT, custom .NET IT, Magento 2 FR/ES), a React Native mobile app, and 600 in-store POS terminals — all within an 18-month, $42M programme delivered by a predominantly junior engineering team. GDPR Article 7 requires opt-in consent before any customer data processing, with per-country enforcement differences between the EDPB and Italy's Garante della Privacy. PSD2 SCA (EBA, Oct 2024) requires step-up MFA for payments above €50 on EU checkout paths. Building OAuth 2.0, OIDC, PKCE, refresh token rotation, MFA, and a GDPR consent SDK from scratch is a multi-year effort that would consume the Phase 1 engineering budget before the first storefront migrates.

## Decision

We will delegate user authentication, JWT issuance, PKCE, refresh token rotation, MFA, and PSD2 SCA step-up redirects to Auth0 (external identity provider). The Meridian Identity Service will act as a thin enrichment proxy responsible only for: session management, loyalty profile assembly, GDPR consent state, and ingesting CRM webhook events. The Identity Service will not implement authentication flows of any kind.

## Alternatives Considered

1. **AWS Cognito** — rejected because Cognito's hosted UI cannot be customised to render per-country GDPR consent screens meeting both EDPB cross-border data flow requirements and Italy's Garante della Privacy opt-in standards simultaneously; achieving this would require Lambda@Edge interceptors on every login flow for each of Meridian's 8 countries. Auth0's tenant-per-country model with GDPR-ready EU data residency and a first-party Consent Management SDK reduces Meridian's compliance build surface from 8 country-specific Lambda shims to Auth0 Actions configuration.

2. **In-house identity service** — rejected because building and auditing OAuth 2.0, PKCE, refresh token rotation, MFA challenges, and PSD2 SCA step-up flows within Phase 1's 18-month window would require ~6 months of senior security-focused engineering time that Meridian's junior-majority Phase 1 team does not have. Tomás Reyes identified this as the "becoming a new monolith" risk: centralising authentication, consent, SCA step-up, and session management in a single internal service creates a single point of failure identical in blast radius to the regional storefront stacks the programme is replacing. A custom auth service that goes down takes all channels — web, mobile, and 600 POS terminals — offline simultaneously, with no vendor SLA backstop.

## Consequences

**Positive:**
- Auth0 handles PKCE, token rotation, MFA, GDPR consent SDK, and PSD2 SCA step-up redirects; the Identity Service remains thin and testable without security expertise.
- Auth0's EU data-residency tenants satisfy GDPR Article 44–46 restrictions on cross-border data flows without requiring Meridian to build a data-residency layer.
- Phase 1 engineering scope reduced by approximately 6 months; the Identity Service build is a stateless enrichment proxy, not an authentication platform.

**Negative:**
- Auth0 is a runtime dependency for all authentication across all channels simultaneously; a service-level outage blocks logins on web, mobile, and POS with no Meridian-controlled fallback short of cached session tokens expiring.
- Vendor lock-in on the identity contract: migrating away from Auth0 in Phase 3+ requires re-implementing OAuth 2.0 flows, all consent management, and SCA step-up logic from scratch — the cost deferred from Phase 1 becomes a Phase 3 investment if the migration ever occurs.
- Auth0 pricing scales with Monthly Active Users; Meridian must model Phase 2 loyalty-programme MAU growth against Auth0's enterprise tier ceiling before committing to the contract.

## Agent-Readable Summary

Authentication, JWT issuance, PKCE, refresh token rotation, MFA challenges, and PSD2 SCA step-up redirects are Auth0's responsibility. **Do not implement OAuth 2.0 grant flows, token storage, MFA logic, or SCA challenge-response handling inside the Identity Service codebase.** The Identity Service enriches and proxies — it calls Auth0 to validate tokens and assembles loyalty and consent state on top. PSD2 SCA step-up for payments over €50 routes through Auth0's MFA Actions, not through a new Meridian service. Any new authentication requirement (passkeys, biometrics, new country login flow) is an Auth0 configuration task, not an Identity Service code change.

**After Auth0 redirects back post-SCA, Checkout Service MUST validate before calling Stripe `confirm`:** (1) the Auth0 `state` parameter is a one-time nonce tied to the specific PaymentIntent — store it in the user session on SCA initiation and consume (invalidate) it on callback; (2) the Stripe PaymentIntent status is `requires_confirmation`, not already confirmed or cancelled. A replayed Auth0 callback that fails either check must return HTTP 400 with no side effects. Skipping these checks allows a 3DS callback from an abandoned flow to complete a charge the customer did not authorise.
