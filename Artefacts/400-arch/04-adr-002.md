# ADR-002: Route Order Domain Events Through Kafka, Not Synchronous REST

## Context

Stripe sends payment confirmation to Meridian as an async webhook — the customer-facing HTTP response completes before the payment is settled. Checkout Service must not hold the customer response open while OMS creates the reservation, because OMS latency (~20–30ms p95 under normal load) becomes an outage surface during peak traffic — a Black Friday scenario Meridian experienced in 2024. A direct synchronous `POST /reservations` from Checkout to OMS couples their availability: an OMS restart or deployment drops in-flight checkouts.

## Decision

We will have Checkout Service publish an `order.placed` event to the Order Event Bus (Apache Kafka / AWS MSK) immediately after receiving Stripe's payment confirmation webhook. OMS consumes `order.placed` events and creates reservations asynchronously. Checkout considers the transaction complete when the event is durably committed to Kafka — not when OMS acknowledges it.

## Alternatives Considered

1. **Synchronous Checkout → OMS REST call** — rejected because Stripe's async webhook creates a required gap between payment receipt and reservation creation; holding the customer response open on a synchronous OMS call surfaces OMS availability and latency as checkout reliability metrics. Meridian's 2024 Black Friday 40-minute outage originated in a similar synchronous coupling between the storefront and the regional OMS; repeating that coupling in Phase 1 would reproduce the failure mode the $42M programme was funded to eliminate.

2. **HTTP callback choreography (Checkout calls OMS, OMS calls Checkout on completion)** — rejected because without a durable broker, a Checkout Service restart between receiving the Stripe webhook and completing the OMS call silently loses the order event. At 600-store peak throughput with rolling deployments, silent event loss at the reservation step reproduces the 7% click-and-collect cancellation-at-pickup failure mode the Confidence API was built to address — except now the cause is a lost reservation rather than phantom stock.

## Consequences

**Positive:**
- Checkout Service and OMS are independently deployable and independently scalable; an OMS deployment or restart does not degrade in-flight checkouts.
- Kafka's durable log enables OMS to replay events and recover from processing bugs (e.g., a migration that breaks reservation creation) without data loss.
- The eventing boundary enforces that Cart Service, Inventory Service, and Order Service cannot acquire hidden synchronous dependencies on each other — each consumes domain events rather than calling peers directly.

**Negative:**
- Reservation state is eventually consistent: a POS cart lookup (03-flow-instore-cart.mmd) may briefly show a paid cart whose OMS reservation has not yet been committed. This window is typically <1s under normal Kafka lag but must be handled in the POS display (show "Payment confirmed — reservation completing" rather than a hard "No reservation found" error).
- Kafka is a new infrastructure component for Phase 1; the junior team must learn producer/consumer semantics, consumer group management, and DLQ handling. Operational training is a Phase 1 pre-requisite, not a Phase 2 follow-on.

## Agent-Readable Summary

Order placement and reservation creation are asynchronous: Checkout Service publishes `order.placed` to the Order Event Bus (Kafka); OMS is the sole consumer that creates reservations. **Do not add synchronous HTTP or REST calls from Checkout Service to OMS, Cart Service, or Inventory Service for order placement, reservation creation, stock deduction, or fulfillment state updates.** These interactions must transit Kafka. A direct service-to-service call for any of these operations violates the independently-deployable boundary and recreates the synchronous coupling that caused the 2024 Black Friday outage.

**Checkout Service must deduplicate on the Stripe event ID.** Store the `Stripe-Event-ID` header value as a `stripe_event_id` column in the Order Database with a unique constraint. An incoming webhook whose event ID already exists must return HTTP 200 immediately without writing a new Outbox row — it is a replay, not a new order. Failure to deduplicate produces duplicate `order.placed` events in Kafka and double OMS reservations with no error signal.
